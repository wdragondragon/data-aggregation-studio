# 文档命名与归档规范

更新时间：2026-04-17

## 1. 目的

本规范用于约束 `data-aggregation-studio` 项目中的文档命名、目录归档、维护方式与新增流程，避免文档散落、重名、断链和后续难以检索的问题。

适用范围：

- `docs/` 目录下的全部项目文档
- 项目根目录 `README.md`
- 需要长期保留且对多人协作有价值的说明类文件

不适用范围：

- 临时排障笔记
- 纯本地个人草稿
- 自动生成且不需要纳入协作管理的临时输出

## 2. 总体原则

- 统一收口：正式文档统一放在 `docs/` 下，不再散落到 `backend/docs`、`frontend/docs` 或其他模块目录。
- 按用途归档：优先按“文档用途”分类，而不是按“代码模块”分类。
- 命名可检索：文件名应让人不打开文件就能大致判断内容和场景。
- 链接稳定：文档移动后需要同步修复引用，避免产生断链。
- 避免重复：已有同主题文档时，优先补充或合并，不重复创建近义文档。

## 3. 目录分类规则

当前统一目录如下：

- `docs/交接/`
  - 用于交接、架构说明、背景说明、实现边界、角色权限说明。
  - 示例：租户项目交接、多模块实现说明、上线交接说明。

- `docs/运维/`
  - 用于运维、监控、排障、值班说明、保留策略、清理策略、运行限制说明。
  - 如有子类，优先继续分层：
    - `docs/运维/监控/`
    - `docs/运维/部署/`
    - `docs/运维/排障/`

- `docs/测试/`
  - 用于测试用例、测试结果、复测报告、专项验证记录。
  - 每个业务域独立子目录：
    - `docs/测试/数据服务/`
    - `docs/测试/质量指标/`
    - 后续可新增 `docs/测试/工作流/`、`docs/测试/采集任务/`

- `docs/数据库/`
  - 用于数据库结构快照、DDL 说明、恢复脚本说明、结构校验资料。
  - 当前快照建议统一放在：
    - `docs/数据库/结构快照/`

- `docs/规范/`
  - 用于规范、约定、模板、文档治理规则。
  - 当前包含：
    - 本文档

## 4. 文件命名规则

### 4.1 基本格式

统一使用小写英文和中划线命名：

```text
<主题>-<用途>.md
```

推荐：

- `tenant-project-handover.md`
- `data-service-test-cases.md`
- `data-service-test-result-20260416.md`
- `quality-metrics-test-cases.md`
- `document-naming-and-archiving.md`

不推荐：

- `测试文档.md`
- `最终版本(新).md`
- `quality_metries.md`
- `DataServiceTestCases.md`
- `说明1.md`

### 4.2 日期规则

测试结果、复测报告、阶段性记录建议带日期，统一使用 `YYYYMMDD`：

- `data-service-test-result-20260416.md`
- `quality-metrics-test-result-20260417.md`

复测建议追加清晰后缀：

- `data-service-test-result-20260416-round2.md`
- `data-service-test-result-20260416-regression.md`

如必须保留中文语义，也应保持简洁明确，不建议混用括号和空格。

### 4.3 中英文使用规则

- 文件名默认使用英文。
- 文档正文可使用中文。
- 仅在必须和业务术语保持一致时，正文中保留中文模块名。

### 4.4 禁止项

以下命名方式禁止继续新增：

- 含空格
- 含括号
- 含“最终版”“新版”“最新”“副本”等语义不稳定词
- 含连续编号但无业务含义，如 `doc1.md`、`说明2.md`
- 拼写错误但长期保留不修复，如 `metries`

## 5. 新增文档归档规则

新增文档时按以下顺序判断归档位置：

1. 先判断用途，而不是先判断属于前端还是后端。
2. 若是测试类，归档到 `docs/测试/<业务域>/`。
3. 若是运行策略、监控口径、清理影响，归档到 `docs/运维/`。
4. 若是交接、架构边界、权限模型、实现说明，归档到 `docs/交接/`。
5. 若是数据库结构快照、恢复说明、DDL 对照，归档到 `docs/数据库/`。
6. 若是团队规范、模板、治理约定，归档到 `docs/规范/`。

若出现无法归类的新类型，再新增一级或二级目录，不要临时放回模块目录。

## 6. 测试文档专项规则

测试文档统一拆成两类：

- 用例文档：`*-test-cases.md`
- 结果文档：`*-test-result-YYYYMMDD.md`

推荐结构：

```text
docs/测试/<业务域>/
├── <domain>-test-cases.md
├── <domain>-ui-test-cases.md
├── <domain>-api-test-cases.md
└── <domain>-test-result-YYYYMMDD.md
```

说明：

- 一个业务域优先维护一份主用例，专项用例作为补充。
- 测试结果文档应引用对应测试用例文档。
- 新一轮复测尽量使用 `round2`、`regression` 这类稳定后缀，避免中文后缀越来越散。

## 7. 链接与引用规则

- 文档内部引用优先使用相对路径。
- 文档移动后，必须同步修复：
  - 其他文档中的链接
  - `README.md` 或 `docs/README.md` 中的导航
  - 脚本里的默认路径

- 若文件改名，需同步检查：
  - 旧拼写引用
  - 旧目录引用
  - README 中的入口链接

## 8. README 维护规则

- 项目根目录 `README.md` 只保留项目总入口、启动方式和总导航。
- 文档导航统一收口到 `docs/README.md`。
- 每次新增正式文档后，如属于长期可复用资料，应同步补充到 `docs/README.md`。

## 9. 历史文档整理规则

整理历史文档时遵循以下原则：

- 能归类的直接移动到 `docs/` 对应目录。
- 命名明显错误但已被引用的，移动时一并修正文件名与引用。
- 内容高度重复的，保留一份主文档，其他合并或删除。
- 自动生成的结构快照、表结构文件保留原层级，不做人工拍平。

## 10. 新增文档操作清单

每次新增正式文档，建议按这份清单执行：

1. 确认文档用途。
2. 选择 `docs/` 下的目标目录。
3. 按统一格式命名文件。
4. 若为测试结果，补日期。
5. 写入正文。
6. 检查是否已有重复文档。
7. 修复引用或新增导航。
8. 在 `docs/README.md` 中补入口。

## 11. 推荐示例

### 11.1 新增一份服务监控排障说明

应归档到：

```text
docs/运维/监控/data-service-metrics-troubleshooting.md
```

### 11.2 新增一份工作流模块测试结果

应归档到：

```text
docs/测试/工作流/workflow-test-result-20260418.md
```

### 11.3 新增一份权限模型交接文档

应归档到：

```text
docs/交接/permission-model-handover.md
```

## 12. 当前执行约定

从本规范生效后：

- 不再新增 `backend/docs/` 这类分散文档目录。
- 正式文档统一进入 `docs/`。
- 文档目录按用途使用中文命名。
- 文档名统一使用英文中划线风格。
- 测试结果统一带日期。
- 新增长期文档必须补 `docs/README.md` 导航。
