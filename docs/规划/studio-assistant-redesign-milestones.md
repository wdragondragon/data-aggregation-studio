# Studio AI 助手重构里程碑

## 目标边界

本次重构目标是把 Studio AI 助手从“依赖模型自由输出 + 前端强解析/强白名单”调整为“LLM-first 协议化编排 + 内置技能上下文 + 后端工具网关受控执行 + 前端轻展示”的形态。

核心要求：

- LLM 是用户输入理解、意图规划、参数判断和复杂归纳的第一入口；后端工具网关只做能力暴露、协议校验、权限/安全约束和受控执行业务接口，不替代 LLM 做开放式意图推断。
- 所有内部调用使用 Studio 自定义报文规范，不依赖不同大模型厂商的 function call 响应体。
- 基础问答要先拆分用户输入中的问题，再形成有输入、有输出的 loop，尽量由助手继续推进上下文，减少用户反复追问。
- 前端支持回答语言切换，第一版支持中文和英文。
- 前端支持 chat、plan、goal 三种模式切换，其中 plan/goal 面向 Studio 平台功能优化。
- 第一版不实现自动学习，不再调用学习接口；改为内置 skill，保留后续 skill provider 扩展入口。
- 第一版移除按用户菜单权限收缩助手能力目录的逻辑，前端不再承担大量权限/白名单控制。
- 重构后需要围绕 Studio 可达功能做聊天界面或接口级自动化验证。
- 产生的 skill 应尽量使用平台无关 schema，能够复制到其他 agent 平台作为 Studio 助手的下位替代能力。
- 需要脚本辅助的 skill 可以通过 Python 脚本实现，但脚本入口必须作为受控 skill/工具登记，而不是由模型自由生成命令执行。

## 第一阶段

- 后端新增协议化助手输出约束：`studio-assistant-protocol`。
- 后端新增内置 skill registry，替代运行时学习记忆作为默认上下文来源。
- 内置 skill 使用 `studio.skill.v1` portable schema，包含 `id/title/tags/content/instruction/agentUsage`。
- `assistant-protocol` 内置 skill 已扩展为可复制到其他 agent 平台的协议契约卡，包含 `protocolVersion`、`protocolFence`、`protocolSchema`、`examples` 和 provider portability 策略。
- LLM 未启用、配置不完整或 `/assistant/config` 不可用时，后端只返回 `llm.disabled` / error / done，不生成结构化回答、协议动作或本地兜底；Web 端隐藏 AI 助手入口和抽屉。
- 后端向 LLM 注入协议、技能、运行上下文和 operation catalog；由 LLM 拆分问题、匹配技能、按 chat/plan/goal 模式组织回答和下一步动作。
- 后端 `studio-assistant.v1` 的 `loop` 结构已升级为状态化协议：包含 `mode/status/autoContinue/questions/next/evidence/stopReason`，用于表达“问题已拆解、下一步等待工具结果、工具结果回来后自动继续摘要”的闭环。
- 前端助手抽屉已解析状态化 `loop` 并转为过程面板事件，展示问题拆解、自动继续、等待用户确认和工具结果回灌状态；内部协议字段继续保持隐藏，不进入可见聊天正文。
- 前端新增语言和模式切换控件，并随请求提交给后端。
- 前端停止调用 `/assistant/learn`。
- 前端不再保留本地业务 API 兜底执行器；需要读取或变更 Studio 业务数据时，LLM 必须输出 `studio-assistant.v1` 协议动作，前端再通过后端工具网关执行。
- 后端新增 Studio operation catalog skill/provider，使用 portable schema 描述平台页面、读工具、写操作确认策略和默认前端动作。
- 后端新增 `/api/v1/assistant/skills` portable skill 导出入口，汇总内置 `studio.skill.v1` 技能和 operation catalog skill cards，供其他 agent 平台复制使用。
- 后端新增 `assistant.script.execute` 受控脚本工具入口，只执行已登记的 `assistant.script.skill` / `scriptEntrypoints`，当前覆盖 `field-mapping-suggester` 的 stdin-json/stdout-json Python helper，不允许模型输出 shell 命令或任意脚本文本。
- LLM 未启用时不生成 `studio-assistant-protocol`，也不执行打开/读取类平台动作；Web 端隐藏 AI 助手。
- 后端新增 `/api/v1/assistant/operations`，向前端暴露 portable operation catalog。
- 前端助手抽屉打开或发送前会加载后端 operation catalog，并只用后端目录生成 `assistantFeatures` / `assistantCapabilities`；后端目录不可用或为空时，本轮不开放 Studio 操作目录。
- 前端只从后端 `readTools/supportsList/supportsGet` 生成 `studio.feature.list/get` 工具规格；后端目录为空或不可用时不启用本地业务工具目录。
- 后端 operation catalog 的 `readTools` 已携带 `type/tool/purpose/mutation/requiredValues/optionalValues/defaultParams/params`，使其他 agent 平台可以直接按 `studio-assistant.v1` 构造打开、列表和详情读取动作。
- 后端 operation catalog 已下发 `featureActions`，前端只使用该目录生成 `studio.feature.action` 注册表、能力上下文和动作匹配；后端目录不可用时不开放本地业务动作。
- 后端新增工具执行网关 `/api/v1/assistant/tools/execute`，已覆盖 `studio.feature.list/get` 的 dashboard、access、catalog、datasources、models、model lineage、field-mapping-rules、collection-tasks、collection-task-runs、run logs、run-metrics、data-development、workflows、runs、data-services、data-service WebService preview/subscriptions、data-service-metrics、data-ingestion-services、data-ingestion WebService preview/subscriptions、data-ingestion-metrics、protocol-conversions、protocol conversion subscriptions、quality-rules、quality-tasks、quality-task-runs、script-environments、ops-center；并覆盖 `studio.feature.action` 的数据源保存/测试/发现、模型保存/同步/索引重建、字段映射规则保存、Data Development 脚本/SQL 动作、服务发布/下线和订阅类动作、采集任务/工作流/质量任务的保存/预览/校验/发布/触发/调度类动作、质量规则保存/解析/校验/启停、脚本运行环境保存/启停/刷新，mutation 动作必须带 `confirmed=true` 才会由后端执行业务服务。前端对 `studio.feature.list/get/action` 不做本地业务接口降级。

## 第二阶段

- 将更多 Studio 业务能力迁移到后端 skill/operation registry，减少前端动作注册表规模。
- 增加服务端工具执行编排，前端只负责确认和展示。
- 增加 plan/goal 模式下的任务状态、阶段结果和恢复策略。

## 第三阶段

- 增加 skill 自动生成与审核入口。
- 支持按租户/项目/场景隔离的 skill 生命周期。
- 增加 Python 脚本型 skill 的 manifest、参数 schema、执行沙箱和结果摘要协议。
- 增加端到端 UI 自动化回归：基础问答、页面导航、列表/详情读取、plan 模式、goal 模式、语言切换。

## 剩余风险

- 已完成真实后端和真实前端的助手抽屉主链路浏览器联调，并用真实 HTTP 遍历验证了 27 个 operation catalog 的默认只读工具和一个无 payload 的真实确认型写动作；深层业务页面的复杂表单自动填充、复杂 payload 写动作和异常恢复仍主要由 mock UI smoke、真实 HTTP 集成测试和服务端单测覆盖，后续新增页面时应继续把高风险 UI 流程补入真实 smoke 或专项 E2E。
- 前端上下文能力目录和动作注册表只消费后端 operation catalog，`studio.feature.list/get` 已统一使用后端工具网关；后续若新增页面子视图或指标页面，需要继续扩展服务端只读工具覆盖范围，避免重新引入前端本地业务执行器。
- 服务端工具执行编排已接管元模型、系统管理只读分页、数据源、模型、字段映射规则、Data Development、开放服务/接入服务/协议转换、采集任务、工作流、质量规则、质量任务、质量指标问题处理和脚本运行环境的主要 `studio.feature.action`；复杂保存表单的 payload 自动组装、系统管理写动作仍需要继续迁移和做真实 UI 联调。
- 当前只实现了登记脚本入口的受控执行闭环，尚未实现多租户 skill 生命周期、脚本审核、资源配额和更完整的沙箱隔离；后续新增脚本型 skill 时仍需要逐个登记 entrypoint、输入/输出 schema 和安全策略。
