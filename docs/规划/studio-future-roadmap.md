# Data Aggregation Studio 未来规划路线图

更新时间：2026-06-02

## 1. 产品定位

Data Aggregation Studio 的当前定位不是单一 ETL 工具，而是面向数据团队、业务系统和运维人员的一体化数据运营平台。系统已覆盖数据源管理、模型管理、采集任务、数据开发、工作流、数据服务、数据接入服务、WebService、监控日志、质量治理、系统管理和 Worker 下发等能力。

后续建设目标是将系统从“功能型数据平台”推进到“生产级数据运营平台”，让平台不仅能配置和运行任务，还能支撑生产环境中的发布、治理、审计、告警、容量和服务运营。

## 2. 建设原则

| 原则 | 说明 |
| --- | --- |
| 生产可运营 | 所有任务、服务、Worker、队列、日志和异常都应能被统一观测和定位。 |
| 配置可治理 | 数据源、模型、任务、工作流、服务和接入服务应支持版本、发布、回滚和审计。 |
| 服务可交付 | 数据服务、数据接入服务和 WebService 应具备文档、限流、配额、订阅方统计和契约管理。 |
| 运行可观测 | 调度延迟、执行等待、失败率、慢调用、队列积压、Worker 离线等指标应可度量。 |
| 权限可收敛 | 权限应逐步从项目级扩展到数据源、模型、服务、日志、Token 和 Worker 组等资源级。 |
| 安全可追溯 | 敏感数据、凭据、Token、日志和配置变更应具备脱敏、轮换、审计和最小可见范围。 |

## 9. 里程碑建议

| 阶段 | 当前状态 | 目标 | 主要交付物 | 验收标准 |
| --- | --- | --- | --- | --- |
| P0 | 进行中 | 建立生产可运营基础 | 统一运维中心、告警规则中心、配置版本与发布管理 | 值班人员可从一个入口判断系统健康；关键失败可告警；核心配置可回滚。 |
| P1 | 部分进行 | 建立服务化治理能力 | 服务网关能力、数据契约、细粒度权限 | 服务调用可限流、可统计、可约束；字段变更可识别风险；资源访问最小授权。 |
| P2 | 部分进行 | 建立资产与质量闭环 | 智能资产目录、质量问题闭环、配置审计中心 | 资产可发现、质量问题可跟踪、关键配置变更可追溯。 |
| P3 | 部分进行 | 支撑企业级扩展 | 实时接入、安全脱敏、多租户资源治理 | 可覆盖实时链路、安全合规和租户资源治理场景。 |

## 10. 后续推进建议

1. P0 已完成统一运维中心首版，下一步应优先推进告警规则中心，让运维中心发现的问题能主动通知到责任人。
2. P1 与 P0 保持接口兼容，避免服务治理改造破坏现有 REST、SOAP 和接入服务调用方式。
3. P2 在 P0/P1 的指标、审计和权限基础上建设，不提前做重型资产治理。
4. P3 作为企业级扩展，不应阻塞当前平台生产化交付。
