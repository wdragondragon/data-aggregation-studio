## 本轮发现

1. `/data-development` 选择或打开 SQL 脚本时，编辑器 SQL 补全通过 `studioApi.models.listByDatasource(...)` 拉取数据源下全部完整模型。
2. 前端只从完整模型中提取 `physicalLocator/name` 和 `technicalMetadata.columns[].name`，用于 Monaco SQL 表名/列名补全。
3. 旧完整模型列表会返回每个模型的 `technicalMetadata/businessMetadata`、审计字段和其他详情。长期项目主 MySQL8 数据源当前 31 个模型，完整列表约 46.2KB。
4. 该完整模型接口仍适合详情、编辑、采集映射等下钻场景保留；数据开发 SQL 补全应使用专用轻接口，不能直接修改完整接口契约。

## 修复内容

1. 新增 `DataModelSqlHintView`，只返回 `id/datasourceId/name/physicalLocator/columns`。
2. 新增 `GET /api/v1/models/datasource/{datasourceId}/sql-hints`，用于 SQL 编辑器补全。
3. `DataModelService.listSqlHintsByDatasource(...)` 源头查询只选择 `id/datasource_id/name/physical_locator/technical_metadata`，不读取 `business_metadata`、schema、审计字段；响应只输出列名数组，不返回完整 `technicalMetadata`。
4. `DataDevelopmentView.vue` 改为调用 `studioApi.models.listSqlHintsByDatasource(...)`，不再在 SQL 提示链路调用完整模型列表。
5. 新增 `DataModelSqlHintSourceSlimmingRegressionTest`，验证 SQL hints 查询字段不包含 `business_metadata/schema_version_id/created_at/updated_at`，并验证列名去重。

## 是否需要修复

需要，已修复。原因是 SQL 补全只需要表名和列名，原实现却批量加载完整模型定义。由于完整模型接口仍服务详情/编辑等下钻场景，本轮新增专用 SQL 提示轻接口替代前端调用。

## 剩余风险

1. 新 SQL hints 接口为保持跨数据库和现有 JSON 存储兼容，源头仍读取 `technical_metadata` 列来提取 `columns`，但不读取 `business_metadata`，响应也不返回完整技术元数据。若后续 `technical_metadata` 继续膨胀，可考虑把列名索引拆到独立轻表或生成列。
2. 本轮未改变完整模型列表、模型详情和模型同步接口契约。
