- 目标：继续深挖模型列表页是否存在“页面只需要筛选条件，但后端为了筛选读取完整详情对象”的隐形性能问题。

## 发现的问题

涉及页面：
- `/models`

涉及接口：
- `GET /api/v1/models/summaries?datasourceType=mysql8&pageNo=1&pageSize=20`

代码复核确认：
1. 前端模型列表的数据源类型筛选只需要把 `mysql8` 等类型转换为可访问数据源 ID 集合，再查询模型摘要。
2. 修复前 `DataModelService#resolveDatasourceIdsByType(...)` 调用 `DataSourceService#list()`。
3. `DataSourceService#list()` 会读取完整数据源列表视图并水合连接状态、健康趋势、元数据字段等列表详情。
4. 模型摘要接口本身不需要数据源连接状态、健康趋势、业务元数据或技术元数据，这会让 `/models/summaries?datasourceType=...` 的源查询被不必要放大。

## 本轮整改

1. 新增轻量数据源 ID 查询
   - `DataSourceService#listAccessibleIdsByType(String typeCode)`
   - 使用可访问范围查询。
   - 仅选择 `id`、`type_code`。
   - 支持输入类型码的原值、小写、大写匹配。
   - 不触发连接健康水合，也不读取元数据字段。

2. 模型摘要筛选改用轻量入口
   - `DataModelService#resolveDatasourceIdsByType(...)` 改为调用 `listAccessibleIdsByType(...)`。
   - 模型摘要分页查询继续只选择列表所需字段。

3. 增加回归测试
   - `DataSourceListSourceSlimmingRegressionTest#datasourceIdsByTypeShouldSelectOnlyIdAndTypeAndSkipHealthHydration`
   - `DataModelSqlHintSourceSlimmingRegressionTest#modelSummaryTypeFilterShouldUseDatasourceIdLookupInsteadOfFullDatasourceList`
