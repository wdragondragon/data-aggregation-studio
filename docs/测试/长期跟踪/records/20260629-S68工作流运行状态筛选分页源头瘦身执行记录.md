# S68 工作流运行状态筛选分页源头瘦身执行记录

## 背景

- 日期：2026-06-29
- 入口：`http://127.0.0.1:8000/dfs/data-aggregation-studio/runs`
- 账号：`admin / admin123`
- 长期项目：`长期回归测试项目`，项目 ID `2068077680446365698`
- 目标：继续深挖运行列表在筛选状态时是否存在“表面分页、内里全量读取”的隐形性能问题。

## 发现的问题

工作流运行列表默认分页已经按页查询工作流运行 ID，但在带 `status` 参数访问时：

- `GET /api/v1/workflow-runs?status=SUCCESS`
- `GET /api/v1/workflow-runs?status=FAILED`

后端会先按时间窗口查询全部 `workflow_run_id`，再按 200 条批量读取 `run_record` 和 `dispatch_task`，在 Java 内存中派生汇总状态并过滤分页。

这会导致长期项目运行记录增长后，状态筛选请求仍随全量候选运行数增长，违反当前“列表筛选必须在源头分页”的测试目标。

## 本轮整改

1. 提取工作流运行摘要构建逻辑
   - 新增 `buildSummaryItems(...)`，默认分页和状态筛选分页复用同一套当前页摘要构建逻辑。

2. 状态筛选改为 SQL 侧计数和分页
   - 新增 `countWorkflowRunsBySummaryStatus(...)`。
   - 新增 `queryWorkflowRunIdsBySummaryStatus(...)`。
   - 使用 `candidate_runs / status_events / ranked_node_status / summarized_runs` CTE 在 SQL 侧派生工作流运行汇总状态。
   - 状态筛选只返回当前页 `workflow_run_id`，再读取当前页记录构建摘要。

3. 保持详情接口行为不变
   - 本次只收敛列表状态筛选的源头取数范围，不改变工作流运行详情页的节点记录聚合逻辑。
