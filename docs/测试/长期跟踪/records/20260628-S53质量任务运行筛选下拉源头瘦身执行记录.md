- 目标：继续结合页面和代码排查前端可达点中过度获取数据的接口，重点验证运行日志筛选控件是否复用表格列表接口。

## 发现的问题

`/quality-task-runs` 的质量任务筛选下拉只用于：

- 下拉标签：`taskName / ruleName / ruleDimension / granularity`
- 运行行补充摘要：按 `qualityTaskId` 查同一组标签字段

但原页面调用：

- `studioApi.qualityTasks.list()`
- SDK 内部按 `pageSize=200` 翻页拉取全部 `/quality-tasks`

旧接口返回质量任务表格视图字段，包括 `taskCode/status/datasourceName/datasourceTypeCode/modelId/modelName/modelPhysicalLocator/columnName` 等。质量任务列表页确实需要这些列，因此原接口应保留；运行日志筛选应新增轻量选项接口。

## 本轮整改

1. 新增轻量 DTO 和接口
   - `QualityTaskOptionView`
   - `GET /api/v1/quality-tasks/options`

2. 源头查询约束
   - `QualityTaskService.listOptions()` 只 select `id/project_id/task_name/rule_name_snapshot/rule_dimension/granularity`。
   - 不读取 `task_code/status/datasource_id/datasource_name_snapshot/model_id/model_name_snapshot/model_physical_locator/column_name`。
   - 不读取详情字段 `where_clause/resolved_sql_preview/parameter_bindings_json/rule_snapshot_json`。

3. 前端调用调整
   - `QualityTaskRunsView.vue` 的质量任务筛选下拉改用 `studioApi.qualityTasks.options()`。
   - 页面仍保留运行记录分页接口 `/runs/page?qualityTaskOnly=true`，日志下钻仍通过 `RunLogDrawer` 按运行记录 id 获取。
