## 代码二次验证

- `SystemResourceShareSupport#notifyResourceShare` 通过 `NotificationService#activeProjectMemberUserIds(targetTenantId, targetProjectId)` 获取接收项目收件人。
- 修复前 `NotificationService#activeProjectMemberUserIds` 只筛选 `studio_project_member.status = ACTIVE`，未检查 `sys_user.enabled = 1`。
- `StudioUserDetailsService` 登录态明确要求 `user.getEnabled() == 1`；运行态禁用用户登录返回 `401 用户已失效`，因此禁用用户不应继续收到新的站内通知。
- 运行时复现：将禁用用户加入接收项目 ACTIVE 成员后，共享新的 S19 工作流，`studio_notification` 为禁用用户写入 `RESOURCE_SHARE` 通知。
- 影响：禁用账号虽然无法登录，但仍被写入活跃通知，造成通知 fan-out 与账号状态不一致；如果后续账号恢复，可能看到禁用期间不应产生的业务通知。
- 设计收口：通知 fan-out 的收件人入口统一过滤启用账号，`activeProjectMemberUserIds`、`superAdminUserIds` 和 `notifyUsers` 均不再返回或写入禁用账号。

## 修复

- 缺陷编号：`BUG-S19-001`
- 级别：高
- 根因：通知服务收件人解析只基于项目成员或角色关系，未过滤 `sys_user.enabled`，导致禁用账号仍可作为通知收件人落库。
- 修复文件：
  - `backend/studio-infra/src/main/java/com/jdragon/studio/infra/service/NotificationService.java`
  - `backend/studio-test/src/test/java/com/jdragon/studio/test/NotificationServiceRegressionTest.java`
  - `docs/测试/长期跟踪/scripts/studio_s19_notification_fanout_acl_probe.py`
- 修复方式：
  - 新增 `StudioUserMapper` 依赖，根据收件人 ID 批量读取 `sys_user`。
  - `notifyUsers` 在写入前统一过滤 `enabled=1` 的用户。
  - `activeProjectMemberUserIds` 和 `superAdminUserIds` 返回值也过滤禁用账号，避免调用方误用。
  - 保持原有通知列表、未读数、已读、SSE 当前用户隔离逻辑不变。
