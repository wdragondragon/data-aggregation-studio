## 代码二次验证

- `FollowController` 的 `status`、`follow`、`unfollow` 均直接调用 `FollowSubscriptionService`。
- 修复前 `FollowSubscriptionService#validateTarget` 只校验 `targetType` 是否在枚举内、`targetId` 是否存在，并未检查目标记录是否存在、是否属于当前租户/项目或是否通过资源共享可读。
- 运行时复现：接收项目成员无法读取源项目工作流运行 `GET /workflow-runs/{workflowRunId}`，但可通过 `POST /follows` 关注同一个不可读 `WORKFLOW_RUN`；也可关注不存在的 `WORKFLOW`。
- 影响：可写入无效个人关注状态，绕过资源可读边界建立跨项目目标引用，后续通知/关注状态可能产生误导性个人状态。
- 设计收口：`follow` 和 `status` 必须要求目标存在且当前项目可读；`unfollow` 保持目标类型/ID 格式校验和当前用户订阅范围更新，允许修复前遗留或分享撤销后的关注记录被幂等关闭。

## 修复

- 缺陷编号：`BUG-S18-001`
- 级别：高
- 根因：关注服务只校验目标类型和 ID 形态，没有把目标存在性、当前租户、当前项目和资源共享可读性纳入 `follow/status` 边界。
- 修复文件：
  - `backend/studio-infra/src/main/java/com/jdragon/studio/infra/service/FollowSubscriptionService.java`
  - `backend/studio-test/src/test/java/com/jdragon/studio/test/FollowApiRegressionTest.java`
  - `docs/测试/长期跟踪/scripts/studio_s18_follow_target_acl_probe.py`
- 修复方式：
  - `MODEL_SYNC_TASK`：要求任务存在且属于当前租户/当前项目。
  - `COLLECTION_TASK`、`WORKFLOW`：要求目标存在且通过 `ProjectResourceAccessService.assertReadable`，保留共享资源可关注能力。
  - `COLLECTION_TASK_RUN`：要求运行记录存在、属于当前租户/当前项目，且确认为采集任务运行。
  - `WORKFLOW_RUN`：要求当前项目存在对应 `run_record` 或 `dispatch_task`。
  - `unfollow` 只校验目标类型/ID 格式并更新当前用户当前项目订阅，避免历史无效关注无法取消。
