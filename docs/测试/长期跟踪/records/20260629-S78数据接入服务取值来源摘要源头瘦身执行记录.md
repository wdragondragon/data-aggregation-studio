## 背景

- 日期：2026-06-29
- 入口：`http://127.0.0.1:8000/dfs/data-aggregation-studio`
- 账号：`admin / admin123`
- 长期项目：`长期回归测试项目`，项目 ID `2068077680446365698`
- 目标：继续深挖表格页是否存在“响应已轻量，但后端源查询仍读取详情 JSON”的表面轻、内里重问题。

## 发现的问题

涉及页面：
- `/data-ingestion-services`

涉及接口：
- `GET /api/v1/data-ingestion-services?pageNo=1&pageSize=10`

代码复核确认：
1. 前端表格 `DataIngestionServicesView.vue` 的“取值来源”列只使用 `row.sourcePositions` 渲染 `JSON Body / Form Body / Header / Query`。
2. 该页面编辑、调试等下钻操作会跳转到 `/data-ingestion-services/{id}/edit`，详情页会按 id 单独加载完整配置。
3. 修复前 `DataIngestionService#list(...)` 为了生成 `sourcePositions`，在分页源查询中选择 `field_mappings_json`。
4. `field_mappings_json` 是接入服务完整字段映射配置，包含每个字段的来源、目标字段、类型、默认值、描述等详情数据。
5. 列表响应虽然没有返回 `fieldMappings`，但后端每次打开表格仍读取完整映射 JSON，属于表面轻、内里重。

## 本轮整改

1. 新增源头摘要列
   - `data_ingestion_service.source_positions_json`
   - MySQL 使用 `json`
   - SQLite 使用 `text`
   - 实体新增 `DataIngestionServiceEntity#sourcePositionsJson`

2. 保存时同步摘要
   - `DataIngestionService#save(...)` 在规范化字段映射后，从 `DataIngestionFieldMapping.sourcePosition` 派生摘要。
   - 摘要只保存 `BODY/FORM/QUERY/HEADER` 等小字段。
   - 完整 `field_mappings_json` 保留给详情页、调试、发布和开放调用链路使用。

3. 列表源查询瘦身
   - `DataIngestionService#list(...)` 改为选择 `source_positions_json`。
   - 不再选择 `field_mappings_json`、`writer_options_json`、`webservice_config_json`。
   - `toListView(...)` 从摘要列组装 `sourcePositions`。

4. 历史数据回填
   - `StudioSchemaUpgradeService` 自动补列。
   - 应用升级时解析历史 `field_mappings_json`，一次性回填 `source_positions_json`。
   - SQL delta `20260629-data-ingestion-source-positions-delta.sql` 负责幂等补列；精确回填由 Java 升级逻辑执行。

5. 增加回归测试
   - `DataIngestionServiceListSourceSlimmingRegressionTest`
   - `StudioSchemaDriftRegressionTest`
