## 本轮确认问题

1. 数据服务访问日志与指标页
   - `POST /data-service-metrics/access-logs/query` 使用 `selectPage(baseLogQuery...)` 读取完整 `data_service_access_log`。
   - 列表页只展示服务、订阅、状态、耗时、错误摘要、缓存、行数、客户端字段，但接口返回 `systemLog`、`logObjectBucket`、`logObjectKey`、`logSizeBytes`、`logCharset`、`logArchiveStatus`、`logArchiveError` 等完整日志字段。
   - `dashboard/query`、`api-stats/query` 通过 `loadContext` 聚合日志时也读取完整日志实体。
   - `options()` 和服务上下文查询读取完整数据服务定义与订阅实体，包含 `customSql`、WebService 配置和 token hash/masked 等列表筛选不需要的字段。
   - 判定：真实存在“列表返回重、聚合源头重、服务筛选源头重”。

2. 数据接入访问日志与指标页
   - `POST /data-ingestion-metrics/access-logs/query` 使用完整接入访问日志实体返回表格。
   - 接入详情抽屉从列表行读取 `systemLog`，但完整日志已有 `InvocationLogDrawer` 按 id 下载入口。
   - `dashboard/query`、`api-stats/query` 和 options 服务/订阅查询同样读取日志与服务配置大字段。
   - 判定：真实存在列表下钻数据预载和聚合源头过取。

3. 协议转换访问日志页
   - `POST /protocol-conversion-metrics/access-logs/query` 返回完整 `ProtocolConversionAccessLogView`，包括 `systemLog` 和日志归档定位字段。
   - 页面详情的四阶段 Trace 已按 `GET /protocol-conversion-metrics/access-logs/{id}/trace` 获取，完整日志按 `GET /invocation-logs/protocol-conversions/{id}/download` 获取；列表无需携带完整系统日志。
   - `options()` 读取完整协议转换服务配置，包含多段 JSON、模板和目标请求配置。
   - 判定：真实存在列表返回重和服务筛选源头重。

## 本轮整改

1. 新增轻量列表 DTO
   - `DataServiceAccessLogListView`
   - `DataIngestionAccessLogListView`
   - `ProtocolConversionAccessLogListView`
   - 三类 DTO 仅包含表格、摘要详情和完整日志入口需要的 id、服务/订阅快照、时间、耗时、状态、错误摘要、客户端和计数字段。

2. 后端源头白名单
   - 数据服务和数据接入分页列表新增 `accessLogListQuery(...)`，从 SQL 层排除 `systemLog/logObject*`、归档状态、BaseDefinition 元字段。
   - 数据服务和数据接入聚合查询新增 `metricLogQuery(...)`，dashboard/api-stats 仅读取聚合计算需要字段。
   - 协议转换分页列表新增 `accessLogListQuery(...)`，排除完整日志、归档定位和元字段。
   - 三类 options 服务/订阅查询均增加 `.select(...)`，排除 `customSql`、字段映射、协议转换配置、token hash/masked 等筛选框不需要字段。

3. 前端契约和页面
   - API SDK 三个 `queryAccessLogs` 返回类型改为轻量 `*AccessLogListView`。
   - 三个访问日志页面改用轻量列表类型。
   - 数据接入和协议转换详情里的“系统日志”改为“日志摘要”，完整线程日志继续通过“完整日志”按钮按 id 获取。
