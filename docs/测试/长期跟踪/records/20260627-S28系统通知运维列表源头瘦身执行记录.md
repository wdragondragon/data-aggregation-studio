# S28 系统通知运维列表源头瘦身执行记录

## 背景

- 日期：2026-06-27
- 入口：`http://127.0.0.1:8000/dfs/data-aggregation-studio`
- 账号：`admin / admin123`
- 长期项目：`长期回归测试项目`，项目 ID `2068077680446365698`
- 目标：继续结合页面和代码排查系统管理、消息中心、统一运维中心的列表/分段列表过度取数，以及 mutation 后刷新范围过大的问题。

## 本轮确认问题

1. 系统用户列表
   - `GET /users` 返回前会清空 `passwordHash`，但源查询先读取完整 `sys_user` 实体，再做 sanitize。
   - 列表页仅展示 `username`、`displayName`、`enabled`、`createdAt`，编辑弹窗不需要列表预载密码或外部账号信息。
   - 判定：真实存在“表面轻、内里重”，且密码字段不应进入列表源查询。

2. 消息中心与站内信快照
   - `GET /notifications` 和 `GET /notifications/snapshot` 源查询读取完整 `studio_notification`，并返回 `payloadJson`。
   - 前端点击通知只使用 `targetPath`、`targetTenantId`、`targetProjectId` 做上下文切换和跳转，不使用 `payloadJson`。
   - `markRead/openNotification/markAllRead` 后前端会重新拉整页通知列表。
   - 判定：真实存在列表过取和 mutation 后刷新范围过大。

3. 统一运维中心
   - DTO 返回已较轻，但后端源查询 `run_record`、`dispatch_task`、数据服务/接入访问日志、Worker lease 时没有 `.select(...)`。
   - 实际会读取 `payloadJson`、`resultJson`、`systemLog`、`clientIp`、`userAgent`、日志对象存储字段、`capabilitiesJson` 等列表视图不使用的大字段。
   - 判定：真实存在“返回轻、内部重”。

## 本轮整改

1. 用户列表
   - 新增 `StudioUserListView`。
   - `UserManagementService.list()` 改为源头只选 `id/tenantId/deleted/createdAt/updatedAt/username/displayName/enabled`。
   - 前端 SDK `users.list()` 和系统操作按钮类型改为使用 `StudioUserListView[]`。
   - 系统用户保存/删除后只 patch 用户列表当前行，不再刷新 profile 或重载当前 tab。

2. 通知列表与快照
   - `NotificationView` 移除 `payloadJson`。
   - 通知列表、快照和单条已读查询源头只选列表/跳转需要字段。
   - `markAllRead` 只读取 `id/recipientUserId/readAt` 后更新。
   - 通知页单条已读、打开通知、全部已读后改为本地 patch 当前页，不再每次重拉整页列表。

3. 运维中心
   - `queueTasks()` 源头排除 `payloadJson`。
   - `runRecords()` 源头排除 `payloadJson/resultJson` 和日志存储详情，仅保留运行摘要、跳转、耗时和日志状态字段。
   - `serviceLogs()/ingestionLogs()` 源头排除 `systemLog/clientIp/userAgent/logObject*` 等完整日志字段。
   - `workerGroups()` 源头排除 `capabilitiesJson`，Worker 组目标名解析只选名称字段。

## 保留风险

- 运维中心当前长期项目在 24h 窗口内队列、运行异常、服务事件、接入事件和日志异常多为空页；本轮通过接口响应和后端源查询 `.select(...)` 双重证明不再取大字段。后续应在有异常样本时复测非空行字段。
- 运维中心仍按时间窗口加载统计源数据后内存筛选部分事件，本轮只完成字段级源头瘦身；如果后续出现大窗口慢查询，应继续拆为更窄的 DB 条件和分页查询。
- 本轮未新增测试数据，也未清理长期测试数据。
