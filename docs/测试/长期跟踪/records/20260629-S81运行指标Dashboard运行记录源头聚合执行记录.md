## 发现的问题

涉及页面：
- `/run-metrics`

涉及接口：
- `POST /api/v1/run-metrics/query`

代码复核确认：
1. S74 已将运行指标需要的采集任务源/目标绑定改为 `collection_task_metric_binding` 轻量快照，但没有覆盖运行记录聚合本身。
2. 修复前 `RunMetricsService.query()` 仍按筛选条件查询时间窗口内所有 `run_record` 成功/失败明细行。
3. Java 层再逐条判断 legacy、按日期桶累加趋势、按采集任务绑定合并源/目标数据源和模型 TopN。
4. 该页面是 Dashboard 统计视图，只需要聚合后的趋势桶、任务级 TopN 输入和 legacy 计数，不应随 `run_record` 明细行数增长而把全部明细拉到应用层。

## 本轮整改

1. 新增运行指标聚合 SQL provider
   - `RunMetricSqlProvider#selectDashboardBuckets()`
   - `RunMetricSqlProvider#selectDashboardTaskAggregates()`
   - 趋势按 `substr(ended_at, 1, 10)` 先在源端聚合到日桶，再由 Java 兼容 DAY/WEEK/MONTH 分桶展示。
   - TopN 输入按 `collection_task_id` 源端聚合，Java 只负责结合轻量绑定快照生成源/目标数据源和模型 TopN。

2. 新增聚合结果模型
   - `RunMetricBucketAggregate`
   - `RunMetricTaskAggregate`

3. 改造运行指标查询
   - `RunMetricsService.query()` 不再调用 `runRecordMapper.selectList(...)` 拉取运行记录明细。
   - 趋势使用聚合桶行。
   - TopN 使用采集任务级聚合行。
   - `legacyRunCount` 由源端按缺失精确指标列统计。
   - 保持历史语义：`success_records` 缺失但 `read_succeed_records/write_failed_records` 存在时，仍按 `max(read_succeed_records - write_failed_records, 0)` 推导成功记录数，不误判为 legacy。

4. 增加回归测试
   - `MetricsSourceSlimmingRegressionTest#runMetricsDashboardShouldUseSourceAggregatesInsteadOfFullRunRecordRows`
   - 断言运行指标 Dashboard 调用聚合 mapper，不再调用 `RunRecordMapper.selectList`。
   - 断言 provider SQL 包含按日期桶和任务聚合，且不包含 `payload_json/result_json/log_file_path`。
