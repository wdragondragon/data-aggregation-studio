## 发现的问题

以下两个页面的 API 统计区块是表格视图：

- `/data-service-metrics` 的“API 统计”
- `/data-ingestion-metrics` 的“接入服务统计”

旧后端实现中，对应接口：

- `POST /api/v1/data-service-metrics/api-stats/query`
- `POST /api/v1/data-ingestion-metrics/api-stats/query`

都会调用 `loadContext()`，先按时间窗口 `selectList(metricLogQuery)` 拉取全部访问日志，再在 Java 中按服务聚合、排序、分页。访问日志分页接口虽然已经使用 `selectPage`，但同样会通过 `loadContext(..., true)` 额外查询 counter summary 和 bucket summaries，这些统计数据并不用于日志表格。

该行为违反“表格类接口只服务表格视图，源头就应轻量分页”的约定。API 统计表需要保留 p95/p99、成功率、最近访问、缓存命中率等展示字段，因此不适合删字段；应把全量日志搬运改为数据库聚合分页。

## 本轮整改

1. 数据服务 API 统计源头聚合分页
   - `DataServiceAccessLogMapper` 新增 `countApiStats()` 和 `selectApiStatsPage()`。
   - 使用 SQL 按 `service_id` 聚合访问次数、成功/失败、响应耗时、p95/p99、最近访问、缓存命中数据。
   - `DataServiceMetricsService.queryApiStats()` 改为只获取当前页聚合结果，不再 `selectList` 全量日志。

2. 数据接入 API 统计源头聚合分页
   - `DataIngestionAccessLogMapper` 新增 `countApiStats()` 和 `selectApiStatsPage()`。
   - 使用 SQL 按 `service_id` 聚合调用次数、成功/失败、接收/写入/失败行数、响应耗时、p95/p99、最近调用。
   - `DataIngestionMetricsService.queryApiStats()` 改为只获取当前页聚合结果，不再 `selectList` 全量日志。

3. 去除表格接口无关 counter 查询
   - `loadContext(..., true)` 不再加载 counter summary 和 bucket summaries。
   - 访问日志分页接口和 API 统计表格接口都只保留服务范围解析，不再额外拉图表统计桶。
