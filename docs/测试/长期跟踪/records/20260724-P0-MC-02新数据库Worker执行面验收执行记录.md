- 计划编号：`P0-MC-02`。
- 本记录从 2026-07-24 新启用的数据库开始，不复用此前因历史密文异常而产生的任何测试结论。

- 当前集群：项目只授权并首选一个启用的 `DEFAULT-LOCAL` 运行集群；受管 HTTP 端点指向独立 Worker。本文不记录端点、认证、数据库或对象存储秘密。
- 操作原则：优先经真实 Web UI 验收；只有 UI 未暴露的实例生命周期字段才读取等价只读接口。

## 阶段 1：单集群交互与 Worker 恢复闭环

### 目标

确认新的数据库在“单 Server 纯控制面 + 单 Worker 执行面”的最小生产等价拓扑中，仍具有唯一集群自动选择、异步恢复执行、同步调用恢复和运行实例可观测性。

### 结果

| 验证项 | 结果 | 证据 |
| --- | --- | --- |
| 单集群数据源适用范围 | 通过 | 新建数据源 UI 将唯一已授权集群自动选为适用集群，并按设计禁用多选下拉，提示“当前只有一个已授权集群，已自动选中”。不是缺少集群。 |
| 项目授权 | 通过 | “运行集群管理 - 项目授权”显示 `DEFAULT-LOCAL` 已授权、首选；“允许手动覆盖”为关闭，符合默认保护策略。 |
| Worker 停机后的异步恢复 | 通过 | Worker 停止时触发的测试工作流先保持排队；使用 IDEA 既有 `StudioWorkerApplication` 配置恢复后，该次运行进入成功，目标/实际集群均为 `DEFAULT-LOCAL`。 |
| 恢复后节点单写 | 通过 | 工作流详情显示总节点 `1`、成功节点 `1`、失败/运行中/未运行节点均为 `0`；未产生重复节点运行。 |
| 恢复后的同步数据服务 | 通过 | Web 数据服务“接口调试”成功返回分页业务数据；Server 返回 HTTP `200`，证明调用仍经 Worker 完成而非停机后遗留失败。 |
| Worker 实例恢复与心跳 | 通过 | Web 运行集群页面显示 `1/1` 在线；实例详情显示一个在线 Worker 和持续推进的最近心跳。只读实例接口同时确认本次启动使用新的 boot ID。 |

### 结论

新数据库中的单集群表单语义、异步排队恢复、同步调用恢复和 Worker 心跳均通过。截图中“适用集群”显示不可编辑在只有一个项目授权集群时是预期交互：系统已保存唯一集群，不需要用户重复选择。若下拉实际显示“无数据”，则应检查当前项目授权，而不是只检查运行集群是否存在或在线。

### 目标

验证三类同步服务在新库中的真实调用记录由实际 Worker 单写，且页面能够明确展示目标/实际集群、调用结果和对应业务摘要。

### 结果

| 验证项 | 结果 | 证据 |
| --- | --- | --- |
| 数据服务日志 | 通过 | 访问日志页同时展示成功的免 Token 查询和两个 `401` 认证失败样本；每条均显示目标与实际集群均为 `DEFAULT-LOCAL`，HTTP 状态、耗时、返回行数和异常摘要可见。 |
| 数据接入日志 | 通过 | 接入运行日志展示多次 `POST` 成功写入，接收/写入成功/写入失败分别为 `1/1/0`，目标与实际集群一致。 |
| 协议转换日志 | 通过 | 协议转换调用日志展示一次 HTTP JSON 到 HTTP JSON 的成功转发，入口与目标 HTTP 均为 `200`，数量为 `1/1/0`，目标与实际集群一致。 |
| 历史调用不混淆 | 通过 | 三类列表均只展示当前项目的资源与日志；当前测试项目名、服务名和运行集群在 UI 中一致。 |

### 结论

三类同步服务的成功、认证失败和转发结果均已在新数据库的真实页面中可追溯，且所有记录指向实际 Worker 集群，没有出现 Server 侧重复写入的迹象。

## 阶段 3：故障关闭与内部端点安全边界

### 目标

在同一新数据库和保留项目中，重新证明目标 Worker 离线时 Server 不会执行兜底；同时复核无法从 UI 直接观察的内部认证、端点隔离、响应上限和幂等安全边界。

### 结果

| 验证项 | 结果 | 证据 |
| --- | --- | --- |
| 同步调用离线失败关闭 | 通过 | 停止唯一 Worker 后，在数据服务“接口调试”点击发送；浏览器请求返回 `503 / SERVICE_UNAVAILABLE`，消息为目标集群没有在线实例，没有 Server 本地回退。 |
| 异步调用离线排队 | 通过 | Worker 离线期间，从工作流 UI 触发保存的默认集群；运行列表显示“排队中”、目标为 `DEFAULT-LOCAL`、实际集群为空、节点为 `1 node(s) queued`。 |
| 恢复后单次执行 | 通过 | 使用 IDEA 已有 `StudioWorkerApplication` 配置重新启动 Worker；同一排队工作流随后成功，目标/实际集群一致、总节点 `1`、成功 `1`，没有重复节点。 |
| 同步调用恢复 | 通过 | Worker 恢复后再次在同一数据服务调试页发送，浏览器请求返回 `200`。 |
| Server 路由与端点边界 | 通过 | JDK 17 定向执行 `RuntimeInvocationRouterTest`：`31/31` 通过，覆盖同编码集群仍走 Worker、离线 `503`、无本地 fallback、受管 Header 不能被调用方覆盖、响应上限、跳转/连接 Header 过滤、认证标记和租户隔离。 |
| Worker 内部认证与幂等 | 通过 | JDK 17 定向执行 `InternalApiTokenFilterTest`、`InternalRuntimeInvocationControllerDebugTest` 和 `RuntimeInvocationIdempotencyServiceTest`：合计 `24/24` 通过，覆盖错误内部 Token、业务 `401` 与传输认证区分、请求体上限、受管 Header 隔离、写入重放、并发唯一约束和响应密文上限。 |

### 结论

本轮在新数据库中直接复验了同步 `503`、异步排队、IDEA 配置恢复、单次执行和同步恢复闭环。结合同轮 55 项路由/Worker 安全自动化，当前本地单 Server + 单 Worker 已具备替代旧 Server 插件执行模式所需的核心运行语义。

## 阶段 4：本地证据收口

### 审计结果

- 新库 UI 验收覆盖了数据源唯一集群自动选择、项目授权、模型依赖的数据服务调试、工作流异步运行、三类同步服务日志、Worker 离线、排队、IDEA 配置恢复和心跳恢复。
- 两轮数据服务调试分别取得 Worker 离线 `503` 与恢复 `200`；同一次停机期间新建的工作流运行从“排队中”转为成功，节点仍为 `1/1`，因此这不是只依赖旧运行记录的间接判断。
- 路由器定向 `31/31`、Worker 内部认证/请求边界/幂等定向 `24/24` 均以项目 JDK 17 复验成功。此前本轮本地全量、SLB 模拟、对象存储协议和回滚演练记录仍作为互补证据保留，但不与新库 UI 记录混淆。
- 当前 Worker 已由 IDEA 既有运行配置恢复，运行集群 UI 显示 `DEFAULT-LOCAL` 为启用、在线、`1/1` 实例且心跳持续推进。
- 未修改运行参数、未删除测试项目或测试资源，未在文档中写入认证、端点、数据库或对象存储秘密。

### 本地结论

对于本地单 Server + 单 Worker 生产等价拓扑，当前证据足以支持以纯控制面 Server + Worker 执行面替代旧的 Server 插件执行版本。仍不能由本地结果推导“生产环境已验收”：真实 HTTPS SLB、OMS/Worker Pod 网络隔离、生产 OSS 的 ACL/容量/生命周期/高可用，以及发布窗口的应用级回滚仍必须按生产验收手册独立执行。
