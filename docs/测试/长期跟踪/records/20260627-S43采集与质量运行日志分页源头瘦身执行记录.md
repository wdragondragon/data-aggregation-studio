# S43 采集与质量运行日志分页源头瘦身执行记录

- 执行时间：2026-06-27
- 前端入口：http://127.0.0.1:8000/dfs/data-aggregation-studio
- 后端服务：IDEA `StudioServerApplication`，`NACOS_SERVER=127.0.0.1:8848`
- 长期项目：`长期回归测试项目` / `2068077680446365698`
- 测试账号：`admin/admin123`
- 数据策略：长期测试数据不清理；本轮未新增业务数据。

## 本轮发现

1. `/collection-task-runs` 和 `/quality-task-runs` 均调用旧 `GET /runs`，一次拉取全部 `runRecords` 后在前端做状态筛选和分页。
2. 长期项目实测旧 `GET /runs` 返回 255 条、约 306KB；采集任务日志页实际只展示 10 条当前页，页面总量为 117 条采集记录。
3. 旧接口同时返回队列和历史运行集合，仍可能有兼容用途；采集/质量运行日志表格不应直接修改旧接口契约。
4. 采集日志页原本还会本地排除 `collectionTaskId == null` 的记录，质量日志页排除 `qualityTaskId == null` 的记录；新分页接口必须把这类域过滤下推到 SQL，避免页面语义变化。

## 修复内容

1. 新增 `RunRecordPageView`，返回 `pageNo/pageSize/total/items`，并保留页面统计卡需要的 `failedCount/runningCount/successCount`。
2. 新增 `GET /runs/page`，支持 `collectionTaskId`、`qualityTaskId`、`workflowDefinitionId`、`collectionTaskOnly`、`qualityTaskOnly`、`status`、时间范围和分页参数。
3. `RunService.listRunRecords(...)` 使用 `selectPage` 直接读取运行记录摘要列，不读取 `payloadJson/resultJson/log*`；状态统计使用 `selectCount`，不先查全量再裁剪。
4. `/collection-task-runs` 改用 `collectionTaskOnly=true` 的分页接口；状态筛选和页码变化只刷新当前页。
5. `/quality-task-runs` 改用 `qualityTaskOnly=true` 的分页接口；状态筛选和页码变化只刷新当前页。
6. 新增回归断言覆盖分页路径使用 `selectPage`、不调用运行记录全量 `selectList`、摘要字段不含日志和 payload 大字段。

## 是否需要修复

需要，已修复。原因是采集任务日志页和质量任务日志页都是表格视图，已有按运行记录 id 下钻日志接口；主表不应通过旧 `/runs` 全量拉取全部运行记录再做本地分页。

## 剩余风险

1. 旧 `/runs` 为兼容入口仍返回全量集合；当前两张运行日志表已切换 `/runs/page`。后续若发现其它页面仍依赖旧接口做表格，应继续拆专用分页入口。
2. 扩展验证时 `RunMetricsApiRegressionTest` 暴露一个历史兼容问题：旧 `/runs` 在源头瘦身后不读取 `resultJson`，直接插入且未回填指标列的遗留记录无法从 JSON 回填 `metricSummary.collectedRecords`。本轮未修复该非分页问题，建议后续作为“遗留运行指标回填/兼容”专项处理。
