## 发现的问题

涉及页面：

- `/data-service-metrics`
- `/data-ingestion-metrics`

涉及接口：

- `POST /api/v1/data-service-metrics/dashboard/query`
- `POST /api/v1/data-ingestion-metrics/dashboard/query`

代码复核确认：

1. 两个 dashboard 首屏展示总览卡片、访问/调用趋势、响应时间趋势、成功率趋势、错误分布、Top 慢服务、Top 失败服务、订阅方排行。
2. 这些视图都只需要时间窗口内的聚合结果，不需要访问日志明细。
3. 修复前 `DataServiceMetricsService#queryDashboard` 和 `DataIngestionMetricsService#queryDashboard` 会调用 `accessLogMapper.selectList(metricLogQuery(...))`，把当前时间窗口内所有匹配访问日志拉回 Java 内存，再聚合、排序、截断 TopN。
4. 虽然 `metricLogQuery` 已避开 `systemLog/logObject*` 等重字段，但访问量增长后仍会随日志行数线性放大，属于“源头未聚合”的过度取数。

## 本轮整改

1. 新增聚合桶模型
   - `OpenServiceDashboardBucketSummary`
   - 承载 dashboard 时间桶所需的访问量、成功/失败、行数、缓存命中、响应时间聚合值。

2. 新增源头聚合 SQL Provider
   - `OpenServiceMetricSqlProvider`
   - 为数据服务和数据接入分别提供 summary、bucket、error distribution、Top 服务、订阅方排行聚合 SQL。
   - 使用数据库 CTE/window function 计算 P95/P99，只返回聚合行，不返回访问日志明细。

3. 改造 dashboard service
   - `DataServiceMetricsService#queryDashboard` 改为调用聚合 mapper 方法。
   - `DataIngestionMetricsService#queryDashboard` 改为调用聚合 mapper 方法。
   - 保留访问日志列表和 API 统计表格接口原契约；本轮只收敛 dashboard 首屏链路。

4. 增加回归测试
   - `OpenServiceMetricsApiStatsSourceSlimmingRegressionTest`
   - 新增断言：两个 dashboard 不得调用 `accessLogMapper.selectList(...)`，不得依赖 counter 全页读取路径，必须调用聚合 mapper。
