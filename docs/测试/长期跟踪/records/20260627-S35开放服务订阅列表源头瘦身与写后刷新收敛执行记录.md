## 本轮发现

1. 数据服务、数据接入服务、协议转换服务的订阅弹窗只展示订阅名、Token 掩码、启停状态、最近使用/轮换等字段，但后端 `listSubscriptions` 未裁剪字段，会读取 `tokenHash` 后在 DTO 组装阶段丢弃。
2. 三类订阅列表为了校验服务可读性/可写性，会先通过完整 `selectById` 读取服务定义；这些服务定义包含 `customSql/webserviceConfigJson/fieldMappingsJson/targetBodyTemplate` 等订阅弹窗不需要的大字段。
3. 三类前端订阅弹窗在创建、重新生成、停用、启用后都重新调用 `listSubscriptions`，单条订阅变更后刷新范围过宽。

## 修复内容

1. 三类服务后端新增订阅专用轻量 service reference 校验，从源头只查 `id/tenantId/projectId`，不读取完整服务配置。
2. 三类订阅列表查询从源头只选择弹窗需要字段：`id/tenant/project/deleted/createdAt/updatedAt/serviceId/subscriptionName/tokenMasked/enabled/createdBy/lastUsedAt/rotatedAt/rotatedBy`，排除 `tokenHash`。
3. 只用于同名启用订阅存在性判断的查询压缩为只选 `id`。
4. 三类前端页面新增 `upsertSubscriptionRow()`，订阅创建、轮换、停用、启用后只 patch 当前弹窗内订阅行并本地排序；打开弹窗时仍按需调用列表接口。
5. `SubscriptionTokenRotationRegressionTest` 增加三类订阅列表 SQL select 断言，覆盖 `token_hash` 和完整服务配置字段不被选择。

## 是否需要修复

需要，已修复。原因是订阅弹窗列表存在敏感 token hash 的源头过取，且订阅单行变更后刷新整个订阅列表，不符合当前 Studio 的轻量视图和窄刷新约定。

## 剩余风险

1. 本轮通过 API 遍历验证了长期项目已有订阅数据，但未新增订阅；长期测试数据按约定保留。
2. 前端订阅本地排序按启用状态和创建时间模拟后端排序；极端情况下若后端排序规则继续扩展，需同步更新本地排序。
