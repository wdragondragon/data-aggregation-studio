# 数据服务监控 90 天明细清理影响说明

更新时间：2026-04-16

## 背景

数据服务开放 API 调用会写入 `data_service_access_log` 明细表，明细默认保留 90 天。为了避免明细清理后影响全局累计统计，当前已新增 `data_service_access_counter` 计数兜底表，用于沉淀按小时聚合的访问计数。

## 已用计数表兜底的统计

- 总访问次数
- 成功次数
- 失败次数
- 成功率趋势
- 访问量增量趋势与总量趋势
- 输出数据量增量趋势与总量趋势
- 已开启缓存请求次数
- 缓存命中次数
- 缓存未命中次数
- 未开启缓存请求次数
- 缓存命中次数增量趋势与总量趋势

## 90 天明细清理后仍会受影响的统计

- 响应时间趋势：平均耗时、最大耗时、P95、P99 目前依赖访问明细中的 `duration_ms`，明细清理后无法还原历史耗时分布。
- 总览响应耗时指标：平均响应、最快响应、最慢响应、P95、P99 若查询窗口覆盖已清理区间，目前只能基于仍保留的明细计算。
- 错误分布：按 HTTP 状态或业务错误码聚合失败调用，目前依赖明细中的 `http_status`、`error_code`，清理后只代表保留期内错误分布。
- API 统计表：每个服务的最快响应、最慢响应、平均响应、P95、P99、最近访问时间目前依赖明细，清理后只代表保留期内数据。
- Top 慢 API：按 P95 和最大响应时间排序，目前依赖明细，清理后只代表保留期内慢请求情况。
- Top 失败 API：当前基于明细聚合服务级失败情况，清理后只代表保留期内失败情况。
- 订阅方排行：当前基于明细聚合订阅方调用量、失败率、平均耗时，清理后只代表保留期内订阅方表现。
- 访问日志明细页：该页面按设计展示明细日志，清理后无法查看 90 天前的单次请求详情。

## 后续可选增强

如需让上述统计也跨越 90 天稳定展示，可以新增更细的聚合快照，例如：

- 服务/订阅/小时维度耗时聚合：`duration_sum`、`duration_min`、`duration_max`、`duration_count`。
- 耗时分位统计：保存 P95/P99 近似桶或每日分位快照。
- 错误分布聚合：按服务、订阅、HTTP 状态、错误码、小时维度沉淀失败次数。
- 最近访问快照：按服务保存最后一次访问时间，避免明细清理后丢失历史最近访问。

这些增强会增加少量存储与写入复杂度，建议在确认需要跨 90 天查看性能和错误分布后再补。
